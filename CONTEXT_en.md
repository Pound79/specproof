# specproof glossary

[日本語](./CONTEXT.md) | English

specproof connects specifications, implementation and features through three layers: methodology skills, a traceability engine and framework scaffolds. Design decisions live in `docs/adr/`.

## Language

| Term | Meaning | Avoid |
|---|---|---|
| Spec | An authoritative description of behavior under an ATX heading in an in-repository Markdown file. The default level is 2 (`##`). Set `headingLevel` to select levels 1–6. Drift is detected at section level. External-only documents, such as a Notion page, cannot be hashed as a spec reference. | “Document” or “design document” without indicating authority |
| Feature | A black-box Gherkin `.feature` describing behavior observable to the user, independently of the implementation. Keep selectors, URLs used as implementation details and internal APIs out of the steps. | “Test” or “test case” when referring to the contract |
| Bootstrap draft | A first draft generated by reading existing code and saved in a scratch directory. It captures current behavior for review. A human decides what should become authoritative. | “Generated feature”, “automatic feature” |
| Blessed feature | A feature a human has reviewed, edited to include intent (boundaries, error paths, roles and rationale references) and promoted to `featuresDir`. It provides an independent RED target for specproof-implement. | “Final feature”, “production feature” |
| Draft marker | The Gherkin comment `# specproof: draft`. A reviewer removes it on promotion. If it remains in `featuresDir`, `specproof-check --strict` fails with `unreviewed-draft` and specproof-implement stops. The legacy marker `# bdd-kit: draft` is recognized too. | “TODO comment” |
| Drift | A deterministic SHA-256 difference between the blessed spec/impl/feature baseline and the current state. A semantic disagreement found before a baseline exists is a separate question. | Using “drift” for an initial inconsistency |
| Bless | A human decision to accept the relationship among spec, implementation and feature and update the corresponding hashes in the manifest. | “Approve” without specifying which baseline is updated |
| Rationale document | A human-authored record of design reasons, internal constants, non-functional requirements and distinctions such as authorization status codes that the UI cannot expose. AI does not generate it. | “Specification” when the distinction matters |

## Adoption modes

Both modes start at `/specproof`.

- **Brownfield (catch-up)** adds E2E coverage to an existing product. Start by extracting a spec outline or by bootstrapping a feature draft once from the implementation. The initial suite often has many `@red-contract` and `@human` conditions. Avoid calling this a retrofit without explaining the direction.
- **Greenfield (spec-first growth)** starts with a spec and a feature in a product under development. The new-feature skill creates the RED contract, then implementation makes it GREEN. Completion has the meaning below. “New project” and “TDD mode” alone omit that contract.

## Completion and tags

The fixed state tags give tools that consume acceptance criteria a shared vocabulary.

| Term | Meaning |
|---|---|
| `@draft` | An idea awaiting a decision. The E2E runner excludes it and it lies outside the accepted scope. Distinguish it from the unreviewed *file* marker `# specproof: draft`. |
| `@red-contract` | A condition awaiting implementation. Run it and observe RED until it passes, then have a person remove the tag. With `@human`, a person verifies it and removes the tag. Project selectors and ordinary filters such as `--grep` and smoke's exclusion of the configured `tags.slow` tag still apply. Never use `--grep-invert @red-contract` to hide these cases. |
| `@human` | A condition a person checks and records. E2E excludes it. specproof counts it and the team maintains the confirmation record externally. A plain “skip” loses this distinction. |
| `@out-of-scope` | A declaration outside acceptance. E2E excludes it and the census counts it separately. Put it on the scenario with an immediately preceding reason comment. Without a reason, or if inherited from Feature, Rule or Examples, check emits `missing-reason`. Stats rejects it on Examples and in combination with `@red-contract`. |
| `@skip`, `@fixme`, `@fail` | Prohibited tags that disable scenarios or make their failure expected (`@fail` in playwright-bdd). Check emits `disallowed-tag` and `specproof-stats --strict` fails. A broken scenario stays RED until repaired. |
| Done | Every accepted condition (excluding `@draft` and `@out-of-scope`) has an actual GREEN run or a human confirmation record, with zero `@red-contract` and no prohibited tags. `specproof-stats --strict` checks only the static conditions. Add it to CI to enforce that part. The bundled drift workflow runs `specproof-check --strict`. Keep human evidence outside specproof. |
| Testability backlog | Product changes needed to automate human checks, e.g. email capture, a deterministic clock, failure injection, or idempotent teardown. When a seam exists, move the condition to `@red-contract` and automate it. |
